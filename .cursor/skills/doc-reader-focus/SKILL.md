# 文档读者信号（去过程噪声）

## Overview

你在写给**后续读者**（实现的人/AI、执行 Skill 的 AI），不是写会议纪要。  
落笔前先回答：**这份文档是什么角色？读者必须关心什么？** 答不上来的句子删掉。

**Violating the letter of the rules is violating the spirit of the rules.**

## When to Use

- 新建或大改：`docs/superpowers/specs|plans/**`、OpenSpec（`openspec/**` 或项目等价目录）、其它 AI 开发范式规格/任务文档
- 编写或修改：`.cursor/skills/**`、`.cursor/rules/**`、`.cursor/templates/**` 说明
- 把探索对话、需求讨论、临时材料「沉淀」进仓库文档时

**When NOT**

- 纯业务代码、样式、配置，且不改任何上述文档
- 用户明确要求保留的过程附录（极少；须写在用户指定位置，默认仍不进正文）

---

## Iron Law

```
NO 过程叙事 IN 终稿文档
先定角色与读者 → 再写仍约束实现的句子
```

对话里出现过 ≠ 文档里要留下。

---

## 1. Skill 与项目的关系（写 Skill 时）

```
Skill 定规范 → 项目按规范执行
禁止：按某仓现状改写 Skill「迁就项目」
```

- **通用化方向**：标题、description、正文写「这类工作怎么做」，不写「某某项目里碰巧怎么做」。
- **项目是采用方**：装了 Skill，代码与目录应对齐 Skill；缺基础设施 → 按 Skill 前置条件补齐，或写明「未具备则先建设」。
- **可改项进 reference**：仅路径别名、目录名等安装差异放 `reference.md` 并标明可改；硬规则（禁直调、模板形态、成功码语义等）留在 SKILL，不随项目稀释。
- **例外**：真正绑死单一业务域时，description 写清适用范围；默认仍按可复用规范写。

**坏：**「WorkBench 接口怎么对接（因为本仓以前这样）」  
**好：**「接口请求规范；采用方须具备 request + 公共类型」

## 2. 先定角色（写什么）

| 角色 | 读者要带走的 |
|------|----------------|
| design / spec | 目标、已确认决策、非目标/边界、方案、验收 |
| plan / tasks / implement | 可执行步骤、涉及文件、验收句 |
| Skill | 何时用、怎么做、禁止做什么（通用规范，非某仓说明书） |
| Rule | 触发时的硬约束（短） |
| 工具包 README | 安装、文件清单、维护；不写「从哪搬来」 |

同一段话若不属于上表任何一列 → **不写**。

---

## 3. 必删（过程噪声）

下列内容**默认禁止**出现在终稿正文（含「目标」段首的参照句）：

| 类型 | 反例 |
|------|------|
| 临时需求/探讨材料路径 | `参照：src/工作台—AI分析结果.md`、`参照材料：src/xxx.md` |
| 外部 demo / 截图溯源叙事 | 「本轮只吸收 demo 主线，不复刻关系图」「见某仓库截图」 |
| 已消化的搬迁故事 | 「从 ForgeKit 搬迁…」「对齐某某项目意图」 |
| 探索对话残留 | 「用户担心…」「经讨论后…」「是否要做 X？建议…」 |
| 征求意见与顾虑原文 | 讨论中的犹豫、解释、取舍过程（未变成决策的） |
| 「帮助 AI 理解」的旁白 | 「为了便于分析…」「本轮探讨结论是…」 |

**自测**：删掉该句后，实现者是否仍知道做什么/不做什么？若是 → 该句本来就多余。

---

## 4. 必留（仍有约束力）

| 类型 | 正例写法 |
|------|----------|
| 产品/范围非目标 | `- 不做 Markdown 渲染预览` |
| 承接 | `- 扫描规则见 2026-08-04-…-design.md`（或 OpenSpec 变更名） |
| 技术/后端边界 | `- 本切片不改 src/apis/regex/**` |
| 已确认决策表 | 表格一行一条，写选择结果，不写如何吵到该选择 |
| 有效风险（可选） | 一条结论式风险 + 缓解；**不写**对话过程 |

把「顾虑」变成文档的唯一合法方式：升格为**决策**、**非目标**或**风险一条**；升格失败则丢弃。

## 5. 改写示例

**坏（过程）：**

```markdown
参照材料：`src/工作台选择文件.md`、ForgeKit demo、截图。
本轮只吸收「选文件夹 → 扫描 → 呈现」，不复刻关系图。
用户担心范围过大，经讨论不做 parse/graph 搬迁。
```

**好（信号）：**

```markdown
## 非目标
- Skills/Rules 分组与关系图
- 搬迁 parse / graph / AI 关系分析
```

**坏：**

```markdown
参照：`src/xxxxxx.md`
```

**好：** 整句删除；把该材料里仍有效的约束写进目标/决策/非目标。

## 6. 项目级 Skill：示例与篇幅

Skill **可以、也常常需要**示例（模板代码、对照表），但示例必须是**可兑现的教学片段**，不是仓库考古链接。

### 示例怎么给

| 做法 | 说明 |
|------|------|
| ✅ 正文内嵌最小可抄模板 | 如 API 函数骨架；读者不依赖仓内另有业务文件 |
| ✅ 约定写清楚前置条件 | 「仅当存在 `@/utils/request` 时适用」——缺则先说明，勿假装有示例模块 |
| ✅ 长内容进同目录 `reference.md` | SKILL 留：何时用 / 铁律 / 短模板 / 禁区；细则、对照表、命名变体、例外表进 reference，正文用相对链接点进去 |
| ❌ 引用临时需求 md / 已删示例路径 / 外仓 demo | 复用项目找不到 → AI 空转或臆造 |
| ❌ 为「完整」把整段业务实现贴进 SKILL | 篇幅爆炸；总结规范 + 最小示例即可 |

### 拆分判据（写 Skill 时）

- SKILL.md 以**可扫完再动手**为准；单文件明显过长、或含「命名变体 / 例外表 / 多场景对照」时 → 同目录拆 `reference.md`，正文用相对链接引用（如 `[细则](reference.md)`）。
- `reference.md` 只放**仍约束执行**的细则，不放过程叙事；项目特异路径集中写在 reference，并标明可改项，便于跨项目复用时只改一处。

## 7. 落笔前检查清单

写完或改完文档，在回复用户前默过一遍：

- [ ] 文档角色明确，未混进会议纪要口吻
- [ ] 无临时文件路径、截图/demo「吸收了啥」叙事
- [ ] 无「用户担心 / 经讨论 / 建议是否」类对话残留
- [ ] 非目标与承接写的是**边界**，不是溯源故事
- [ ] Skill 按通用规范写，非「某项目说明书」；项目应对齐 Skill
- [ ] Skill/Rule 无「对齐某仓库」溯源——只写本包交付与禁区
- [ ] Skill 示例可兑现（内嵌模板或 reference），无空引用
- [ ] 篇幅过长的 Skill 已考虑 `reference.md` 拆分；可改项在 reference
- [ ] 删掉噪声后，目标/决策/步骤/验收仍然完整

---

## 8. 与其它流程的关系

- **brainstorming / 探索对话**：顾虑与征求意见留在对话里；写入 design/spec 时只带升格后的决策。
- **回写 design / plan / 等价规格**：同样去噪声；修订记录 = 日期 + 结果摘要，禁止聊天过程。
- **OpenSpec / 其它 AI 开发范式**：提案、design、tasks 同样适用；不因目录名不同而放宽。

## 维护

本 Skill 只约束「写什么」；不规定 design 章节编号或 OpenSpec 目录结构（那些由对应范式模板负责）。
